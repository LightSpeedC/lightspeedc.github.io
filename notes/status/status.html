HTTPS 対応

発端: 証明書が発行されない状態だった

作業開始時点で https://lightspeedc.com/ は証明書エラー（SEC_E_WRONG_PRINCIPAL）となり接続できなかった。原因は DNS の A レコードが GitHub Pages の旧IPアドレスを指していたことだった。

旧IP（192.30.252.x）は Let's Encrypt による自動証明書発行の対象外。 このため、待っていても証明書は永久に発行されない状態だった。CAA レコード・DNSSEC・_acme-challenge の残骸はいずれも無く、旧IP が唯一の原因だった。

ネームサーバーは 01〜04.dnsv.jp。DNS の伝播は速く、変更から数分で主要な公開リゾルバ（Google Public DNS、Cloudflare）に反映されていた。証明書はその約1時間後に発行された。

Enforce HTTPS の有効化

証明書の発行を確認したのち、親リポジトリと公開資料4件のリポジトリすべてで Enforce HTTPS を有効にした。HTTP でのアクセスは 301 で HTTPS へリダイレクトされる。

gh api -X PUT repos/LightSpeedC/lightspeedc.github.io/pages -F https_enforced=true

混在コンテンツの確認

HTTPS 化にあたり、http:// で外部リソースを読み込んでいる箇所を調べた。docs/react/ の3ファイルに http://fb.me/... のスクリプト読み込みがあったが、いずれも HTML コメント内で無効化されており、実際に読み込まれているのはローカルの /react/js/react.min.js だった。したがって HTTPS 化で壊れたページは無い。

ブランチ運用

develop と master の2本構成とした。release は作っていない。このリポジトリでは release に置いても develop に置いても検証手段が同じ（ローカルの run.cmd のみ）で、通過点にしかならないため。

master は「公開ボタン」そのもの。 Pages の公開ソースが master/docs なので、master への push はその時点で世界に公開される。develop に push している限りは公開されない。

更新の流れ

手順

1. develop で編集・コミット
2. git push origin develop
3. git switch master
4. git merge --no-ff develop
5. git push origin master        ← この push で公開される
6. git switch develop            ← 作業後は develop に戻る

マージは常に --no-ff を使い、fast-forward は行わない。どの単位の作業が公開されたかを履歴から追えるようにするため。

設定変更とプッシュの順序に注意

Pages の設定変更は、プッシュより先に行う。 docs/ へ集約した際、先にプッシュしてから公開ソースを /docs に変更したところ、設定変更前に始まっていたビルドが古い設定（ルート）で走り、トップページが一時的に 404 になった。再ビルドをリクエストして復旧している。

gh api -X POST repos/LightSpeedC/lightspeedc.github.io/pages/builds

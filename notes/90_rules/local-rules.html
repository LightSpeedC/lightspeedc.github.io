ブランチは2本で運用する

適用条件: このリポジトリで作業するとき。

  • develop と master の2本。release は使わない
  • master が GitHub Pages の公開ソース（master ブランチ / /docs）

トップページへの掲載

適用条件: ai-chat-lite で他プロジェクトから掲載を依頼されたとき、および docs/index.html の資料一覧を増減するとき。

依頼の受け付け

  • 掲載依頼は、受け付けた時点から公開・返信まで、確認を待たずに自動で進める。 順序は、反映（docs/index.html・status。日付は「作成日・公開日」）→ commit → publish-master.ps1 で master へマージ・push → ビルド確認 → 依頼元へ返信
  • 共通ルールとの違い（commit・push を指示なしで進める理由）は、「作業の区切りでの commit・公開」に書く
  • 説明は依頼元リポジトリの description を転記する。自分で書き起こさない
  • 反映の前に、依頼元が public で、公開 URL が 200 を返すことを確かめる。満たさなければ、反映せずに報告して止まる。既に載っている依頼（再送）は、再掲載せず、公開済みと返信する
  • 掲載先の章は、依頼が「1章または2章」とあっても、自動で2章にする（先頭に置く）。 依頼元が章を指定していないときも同じ。後でレビューして1章へ移すことはあるが、判断待ちでフローを止めない
  • 依頼が重なったときは、1回の commit・公開にまとめる
  • 返信は、ビルド確認（該当 commit の run が success）と、公開 URL での反映の確認が済んでから送る

並び

  • 1章・2章とも、新しいものを上に置く
  • 既存の並びは動かさない。過去に追加した分を日付順に並べ直すことはしない
  • 関連する資料が続くときは、ひとまとまりのまま扱う（ai-chat 系3件）
  • 1章の MCP Server 学習資料は、依頼により最後に置く（例外）

作成日・公開日

  • 各資料の 公開Web・GitHub バッジの右に、📅 作成: yyyy-mm-dd / 公開: yyyy-mm-dd を置く。 書くのは p.links の末尾の span.pubdate（1・2章とも）
  • 作成日は、リポジトリ名の先頭の日付（yyyymmdd-）。 名前に日付が無いリポジトリは、GitHub のリポジトリ作成日を JST に直して書く
  • 公開日は、このリポジトリの master で、その資料が docs/index.html に最初に載った commit の日。 取り方は git log master --reverse --format=%aI -S<リポジトリ名> -- docs/index.html の先頭行
  • 掲載依頼を受けて資料を足すときも、同じ形で日付を付ける。公開日は、公開する日になる
  • 更新日は、公開日のあとに / 更新: yyyy-mm-dd を付ける。 形は 📅 作成: … / 公開: … / 更新: …。更新日が公開日と同じか、取れないときは付けない
  • 更新日は、リンク先リポジトリの最後の push の日（pushed_at を JST に直したもの）。 README と docs/ だけの更新に絞るのは難しいため、リポジトリ全体の最終更新日で足りるとする。取り方は gh api repos/LightSpeedC/<リポジトリ名> --jq .pushed_at
  • 毎朝5時台に、CronCreate の定期実行で、全リンク先の更新日を見て反映する。 式は 3 5 * * *。起きたら、1・2章の各資料の更新日を取り、span.pubdate と違う資料があれば書き換える
  • 更新日が変わった資料があれば、その場で commit・push・master への公開・ビルド確認まで進める。 変わった資料が無ければ、何もしない。起きた時刻は「月/日 時:分」（JST）で表示する
  • この cron も、セッションを閉じれば消え、最大7日で失効する。開き直したら、共通ルール「セッションを開き直したとき」に従い、指示を待たず張り直す

資料見出し（h2）の虹色

  • 章（h1）とは別に、資料見出し（h2）にも 280°→0° の虹色を割り当てる
  • 刻みは「最も項目数が多い章の等分」で固定（280 ÷ (最多件数 - 1)）。項目の少ない章は途中で止まる
  • 色相は .dc01〜 のクラスに --dh として持たせ、section h2 a（資料へのリンクのバッジ）が hsl(var(--dh, 220), ...) で参照する
  • 資料を増減したら刻みを計算し直し、全章の .dcNN を振り直す

説明とバッジの枠

  • 各資料の説明と、公開Web・GitHub のバッジの行（日付を含む）は、1つの枠でまとめる。 1・2章とも
  • 背景は見出しバッジと同じ色相の淡い色（hsl(var(--dh), 28%, 95%)）。左に同じ色相の 5px のバー（hsl(var(--dh), 58%, 55%)）を置く。幅は見出しバッジに揃える（90%、最小 320px、最大 100%）
  • 骨格は h2.dcNN > a の下に div.item.dcNN、その中に p.desc と p.links。CSS は docs/css/style.css の .item
  • 掲載依頼で資料を足すときも、この形で書く

html2md では status を除外する

適用条件: html2md を走らせるとき。

  • --exclude status.html を必ず付ける
  • notes/status/status.html は HTML だけで運用する。Markdown 版は持たない
html2md --root <プロジェクトフォルダ> --exclude status.html

付け忘れても成功して終わる。 notes/status/status.md と、インライン SVG を切り出した notes/status/images/status-fig01.svg が黙って増える。検査も「指摘なし」で通る。

master へのマージ・push は publish-master.ps1 を使う

適用条件: develop から master へマージして公開するとき。

  • 手作業でコマンドを並べない。tools/80_ops/publish-master.ps1 を使う
  • マージメッセージは事前にファイルへ書き、-MergeMessageFile に渡す
  • タグ名は共通ルール「タグ名」の形（yyyy/mm/dd_master 等）に従う
  • 各ステップの成否を確認してから次に進む。 失敗したらそこで止まる。改行区切りでコマンドを並べて失敗を見逃す事故を防ぐ
tools/80_ops/publish-master.ps1 `
  -MergeMessageFile tmp/merge-message.txt `
  -TagName "2026/09/23_master-02" `
  -TagMessage "AGENTS.md移行・sleepルール・cron待受けルールを反映"

ビルド確認は実時間の sleep で待つ

適用条件: master を push したあと、Pages のビルドを確認するとき。

  • 待ち方・手動依頼・流し直しは、共通ルール「GitHub Pages 公開ルール」＞「push のあとに公開を確かめる」に従う
  • 上書き: 確かめるのは pages/builds/latest ではなく、Actions の run。 Pages API の status は、queued（ランナ待ち）も実行中も building と返り、区別がつかないため。見るのは gh run list の headSha が、push した commit と一致するか
  • 自動で積まれる回と積まれない回が不規則に出る（i260917-01）。待ち時間は 5分（300秒）で、公開の確認は「該当 commit の run が success」まで取る
  • push した時刻・確認した時刻・手動で依頼した時刻を、いずれも「月/日 時:分」（JST）で表示する。 実際にどれだけ待ったかを利用者が見て確かめられるようにする
date "+push: %m/%d %H:%M"
sleep 300 && date "+確認: %m/%d %H:%M（5分待った）" && gh run list --repo LightSpeedC/lightspeedc.github.io --limit 1 --json databaseId,headSha,createdAt

該当 commit の run が現れなければ、手動で依頼する。

date "+手動ビルド依頼: %m/%d %H:%M" && gh api -X POST repos/LightSpeedC/lightspeedc.github.io/pages/builds --jq ".status"

run が queued のまま滞留したときは、手動の再リクエストでは直らない。 走っているジョブを cancel して新しく積むだけで、待ち行列の先頭には入らない。Actions の画面で滞留ジョブを消してから積み直す。公開されている中身は旧版のまま正しいので、URL を叩いても気づけない。

作業の区切りで commit・push、まとまったら公開まで自動で進める

適用条件: このリポジトリの docs/・notes/ の変更を扱うとき。

  • 上書き: 共通ルール「重大な操作の確認方法」・「修正は1点ずつ、確認を重視」では、commit・push は実行語の指示を待つが、このリポジトリでは指示を待たずに進める。 理由は、中身が自分の資料の変更に限られ、develop と master の履歴から戻せるため
  • 作業が一区切りしたら、develop に commit・push する。 載せるファイルは名指しで git add する。メッセージの付け方は共通ルール「git の使い方」に従う
  • まとまった作業が完了したら、master へのマージ・push・ビルド確認まで自動で進める。 手順は「master へのマージ・push は publish-master.ps1 を使う」と「ビルド確認は実時間の sleep で待つ」に従う
  • 「まとまった作業が完了した」とは、依頼1件が済んだときと、記録（issues・status）の反映まで済んだときをいう
  • 掲載依頼と、毎朝の更新日の反映（「作成日・公開日」）は、見つかった時点でこの章の「完了」とみなし、公開まで進める
  • 範囲は、このリポジトリの docs/・notes/ の変更だけ。 ほかのリポジトリ、git reset、履歴の書き換え、ファイルの削除は含めない。それらは、これまでどおり指示を待つ

待受けを cron で回す

適用条件: このリポジトリで ai-chat-lite の待受けを運用するとき。

  • 4時間おき、8・12・16・20・24（0）時に CronCreate で仕込む。 式は 43 0,8,12,16,20 * * *。対象ルームは public
  • 起きるたびに、起きた時刻を 「月/日 時:分」（JST）で表示する
  • 受けた発言のうち当リポジトリに関係するものは、概要を表示する。 関係の有無・報告の要不要の判断は共通ルール「ai-chat-lite（AI 間チャット）の利用」に従う
  • 張り直し・カウント・止めてよい範囲も同じ共通ルールに従う。ここで決めるのは頻度と、起きたときに時刻・概要を出すことだけ
  • 待受けも cron も、セッションを閉じれば消える。cron は最大7日で失効する。 開き直したら、共通ルール「セッションを開き直したとき」に従い、指示を待たず両方を張り直す（待受けは waiters で数えてから、cron はこの章の式で作り直す）
